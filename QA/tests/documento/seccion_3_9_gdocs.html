3.9.2. Alcance y procedimiento

Los casos de base de datos se ejecutaron con sqlcmd sobre los scripts db/01_ddl.sql y db/02_dml.sql del repositorio, sin modificarlos y partiendo de una instancia sin la base persona_db. Los casos de la API REST y de Swagger se automatizaron con Python, y los de las vistas MVC y la integración, con Playwright, que recorre la interfaz y guarda capturas. Las validaciones del servidor y los envíos con datos alterados se comprobaron además con solicitudes HTTP que incluyen el token antifalsificación del formulario.

La documentación de QA se conserva en la carpeta QA/ del repositorio: la matriz, esta copia del documento, las evidencias y los scripts. Los scripts están en QA/tests/, fuera del código de la aplicación, y QA/tests/run_all.sh repite la corrida completa desde un contenedor limpio. Cada evidencia se guardó en QA/evidencias/ con el identificador del caso en el nombre, por ejemplo EV-API-PER-04.txt o EV-MVC-PER-02.png. Los registros creados durante las pruebas se eliminaron al terminar cada script.

La API, Swagger y la revisión del backend se ejecutaron primero en main y luego en la rama del Pull Request como prueba de regresión, con los mismos resultados en ambas ramas. Las vistas MVC y la integración se probaron en la rama del Pull Request, que es la que contiene el frontend. Como evidencia complementaria se ejecutó sin cambios el script tests/mvc-smoke.ps1 del equipo, que terminó con 213 comprobaciones HTTP correctas.

Los casos de revisión se ejecutaron después sobre main integrada. MVC-GEN-05 repitió un flujo completo con Playwright en Chromium (motor de Chrome y Edge), Firefox y WebKit (motor de Safari). MVC-GEN-04, SW-09 y ENT-12 se apoyaron en mediciones automáticas (desbordes y tamaño de letra en tres anchos de pantalla, descripciones del documento OpenAPI y estilos y redacción del documento); el criterio aplicado quedó escrito en la matriz para su confirmación por el responsable de QA.

Las pruebas también confirmaron comportamientos que no incumplen los resultados esperados, pero se registran como oportunidades de mejora. Las columnas de texto son VARCHAR: conservan las tildes y la ñ, pero alteran caracteres fuera del código de página 1252 (por ejemplo, «Nguyễn» se guarda como «Nguy?n»). La cédula es de tipo INT, admite las cédulas de 10 dígitos que comienzan por 1 y rechaza valores desde 2.147.483.648. La API acepta números de teléfono con letras y fechas de estudio futuras. El archivo appsettings.json contiene la contraseña de ejemplo del usuario sa, Swagger permanece disponible fuera del entorno Development y el bloque catch de DELETE atribuye cualquier DbUpdateException a la existencia de registros dependientes.

3.9.5. Limitaciones

  • Solo se dispuso de SQL Server 2022 en Docker. No se probaron SQL Server Express ni LocalDB; el fallo de ALTER AUTHORIZATION se reprodujo con un login sin rol sysadmin.

  • Chrome y Edge no estaban instalados en el equipo de pruebas. Las pruebas de interfaz usaron los motores de Playwright sin interfaz gráfica: Chromium (el de Chrome y Edge), Firefox y WebKit.

  • La concurrencia se evaluó con 20 pares de solicitudes simultáneas sobre la creación de personas. No se realizaron pruebas de rendimiento, carga ni seguridad más allá de la protección antifalsificación, la exposición de errores y las credenciales versionadas.

  • La comparación con el diseño de Figma (MVC-GEN-03) se hizo con el enlace compartido, sin sesión, a partir de capturas de cada marco. Las revisiones de MVC-GEN-03, MVC-GEN-04, SW-09 y ENT-12 aplican criterios escritos en la matriz que el responsable de QA debe confirmar.

3.9.6. Conclusión de QA sobre el Pull Request #2

La rama feature/frontend-mvc compila sin errores ni advertencias con el SDK 6.0.428, no modifica la API REST ni los scripts de base de datos y mantiene los resultados de main en la API, Swagger y el backend. En el frontend se aprobaron 34 de los 40 casos MVC ejecutados y los 8 casos de integración. Los defectos del frontend (DEF-06, DEF-07 y DEF-09) son de severidad baja y no impiden el uso de las operaciones CRUD.

Por lo anterior, QA aprobó el Pull Request #2, que se integró en main el 27 de octubre de 2026 mediante el merge commit 8fc7d80. El caso ENT-07 se repitió sobre un clon limpio de main: la rama integrada compila sin errores ni advertencias y la aplicación responde correctamente en las vistas MVC, la API REST y Swagger. Antes de crear el TAG de entrega conviene corregir los defectos de severidad media DEF-01 y DEF-02, que corresponden al backend y al README, repetir ENT-08 y ENT-09 y ejecutar BD-07 en un equipo Windows con SQL Server Express o LocalDB.
